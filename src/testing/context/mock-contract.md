# Private online Feishu mock

This Worker exists only for the explicitly authorized isolated online test environment. It has no public route, workers.dev URL, management endpoint, source-byte store or outbound internet access requirement. The Gateway calls it through an optional `FEISHU_MOCK` service binding only when `FEISHU_TRANSPORT=mock`; both configured base origins must be the exact `.invalid` mock origins. Missing bindings, missing mode with mock bindings/origins, unsupported modes and unexpected origins fail closed rather than falling back to the public Feishu API.

The Worker uses the same isolated test D1 as the Gateway, with separate `mock_files`, `mock_replies` and `mock_requests` tables from testing-migrations. The test driver creates fixtures and changes modes through authorized D1 operations. Every source resource lookup requires the exact message_id/file_key pair. Replies use the supplied Feishu uuid for durable duplicate suppression and retain only text content and a fake receive ID. Requests retain the source identity, requested Range, status, produced byte count, source outcome and colo, never credentials or bytes. A completed outcome means the mock finished producing its response stream, not that the end customer persisted every byte.

The data generator is shared with local Node mocks using only Uint8Array/ReadableStream APIs. It repeats a precomputed 64 KiB template while overlaying the absolute block number in each block's first 16 bytes, preserving all established hashes and detecting duplicated/reordered whole chunks. Each pull allocates at most 64 KiB; healthy responses use FixedLengthStream and expose exact Content-Range/Content-Length. Fault fixtures can report missing, forbidden, throttle, wrong range, truncated body or delayed headers. Source cancellation observations are best effort and cannot prove notification behavior across every deployed service-binding hop.

The API subset consists of OAuth client_credentials token exchange, paired message-resource GET and bot text-message POST. It validates the fake application credentials, uses a deliberately non-real mock access token, rejects unexpected paths/hosts and offers no general-purpose proxy. Public download authentication behavior remains in the Gateway and is unaffected.
