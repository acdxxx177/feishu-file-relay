## Implementation decisions and observed corrections

- A minimal D1 transaction precedes webhook acknowledgement; all Feishu I/O runs afterward in waitUntil. This avoids acknowledging a callback that could be lost before background processing starts. D1 failures return 503 for redelivery.
- Retry eligibility is persisted at 2/10/60 seconds after the initial validation attempt; actual dispatch occurs on later callbacks or Cron, possibly up to five minutes later. This respects the short HTTP waitUntil lifetime without introducing a queue.
- HEAD is D1-only. A real bytes=0-0 response reads precisely one origin byte, never a whole chunk. PRD's simultaneous D1-only probe and no-source-bytes-in-D1 requirements cannot otherwise return the actual first byte.
- Successful public responses use PRD v1.1 private,no-cache; errors use no-store. This supersedes the older no-store-for-all workflow note.
- Workers rejected redirect:'error' at runtime despite the generated RequestInit type accepting it. Token/API requests now use manual redirects and reject non-success responses, without forwarding credentials to another origin.
- Successful 206 resource responses remain binary regardless of JSON MIME type; API envelopes are parsed only outside this successful resource path.
- Workers stripped manually supplied Content-Length from unknown-length JS streams. Native FixedLengthStream preserves exact public/chunk lengths.
- A canceled native cache write actually left a partial body with the expected Content-Length. Therefore Cache.put completion alone is not assumed atomic: a random-generation completion marker is published only after verified EOF and a successful cache write. Hits require matching marker generation and length, preventing incomplete/stale objects from qualifying.
- Per-read idle timeout defaults to 30 seconds; the one-byte registration probe is bounded by eight seconds. Errors reach the output before potentially slow cancellation cleanup. RPC capabilities are disposed on completion/cancellation.
- The enable_request_signal flag enables incoming disconnect signals. Local HTTP sockets may only notify disconnect when a response is written; a test-only runtime wrapper verifies preheader application cancellation. Two subsequent online mock trials confirmed cancellation before headers at the observed edge; production latency across regions remains unverified.
